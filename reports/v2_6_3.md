# Патч v2.6.3 — единицы σ/Fee для многолотовых позиций, backoff на HTTP 429, тихий режим вычислений

Дата: 27.10.2026. Сессия живой торговли (`--mode watch --preset ALL_ACTIVE`, 5 пар).

---

## 1. Почему в таблице портфеля светились ошибки

Пользователь видел красные ячейки в дашборде `http://127.0.0.1:8099/`. Разбор живой сессии
(лог `logs/multi_v262.log`, 572 строки, 5 пар, 2 300 секунд) дал **две независимые причины**.

### 1.1. Колонка «ошибки» = HTTP 429 (rate limit T-Invest REST)

Всего в логе **5 ошибок**, все в одну секунду `10:53:59` — по одной на пару:

```
10:53:59.194 [WARNING] AFKS_SBER: GetOrderBook AFKS: HTTP 429:
10:53:59.294 [WARNING] IRAO_SBER: GetOrderBook IRAO: HTTP 429:
10:53:59.392 [WARNING] MTLR_SBER: GetOrderBook MTLR: HTTP 429:
10:53:59.497 [WARNING] SPZ6_SRZ6: GetOrderBook SPZ6: HTTP 429:
10:53:59.621 [WARNING] VTBR_SBER: GetOrderBook VTBR: HTTP 429:
```

Трассировок, таймаутов и падений нет. За 7 часов работы набежало 2–4 ошибки на пару —
это **не сбой бота**, а троттлинг публичного REST-шлюза.

Причина: 5 пар × 2 ноги каждые 300 мс ≈ **33 запроса/с**. Бесплатный REST-лимит ниже.

Следом за 429 закономерно появились «рассинхроны стаканов» (нога не ответила) и они
сработали по назначению: тик отброшен, фантомного Z не возникло.

**Что сделано.** Адаптивный backoff в `MultiPresetRunner`:

- `_note_rate_limit()` — при `status == 429` весь цикл опроса уходит в паузу
  (`THROTTLE_MIN_SECONDS = 2 c`), пауза удваивается до `THROTTLE_MAX_SECONDS = 20 c`;
- `_wait_throttle()` — выдерживает паузу и через `THROTTLE_DECAY_SECONDS = 90 c` тишины
  возвращает нормальный темп;
- 429 больше не считается «обычной» ошибкой REST и не спамит лог: пишется одна строка
  на всплеск, а счётчик `rateLimited` показывается в подсказке колонки «ошибки».

Остальные ошибки (500, таймауты) поведение не меняют — тест
`test_other_errors_do_not_throttle` это фиксирует.

### 1.2. Красный σ/Fee (`0.09`) — баг единиц при `quantityLots > 1`

| пара | лотов | σ/Fee в дашборде (было) | при 1 лоте | после фикса |
|---|---|---|---|---|
| VTBR_SBER | 55 | **0.09** | 4.95 | 4.95 |
| MTLR_SBER | 60 | **0.09** | 5.40 | 5.40 |
| IRAO_SBER | 8 | 1.05 | 8.40 | 8.40 |
| SPZ6_SRZ6 | 1 | 1.01 | 1.01 | 1.01 |

Комиссия круга считалась **на позицию** (`fee × lots`), а σ спреда — **на один лот**.
Отношение падало ровно в число лотов, и `minSigmaToFeeRatio = 1.30` блокировал любые входы
(в счётчике `volFilterSkips` росли отсечки при живом Z). Именно поэтому за сессию
не было ни одной сделки на VTBR/MTLR.

**Что исправлено** (σ умножается на число лотов — обе величины становятся «на позицию»):

- `bot_a/engine/fsm.py::_maybe_enter` — сам фильтр;
- `bot_a/services/live_dashboard.py::_entry_diagnostics` — чек-лист «почему не входим»;
- `bot_a/services/multi_preset.py::_pair_payload` — колонка `S/Fee` в общем дашборде.

**Регресс-тест.** `tests/test_v26.py::test_sigma_to_fee_ratio_is_lot_invariant`:
при 1 и 55 лотах отношение совпадает (расхождение < 1 %), и vol-фильтр ведёт себя
одинаково (`volFilterSkips` равны).

**Проверка на живых данных** (VTBR, 55 лотов, 11:47 МСК):

```
vol: σ_leg1 5.2029 / Fee 1.5760 = 3.30 (нужно ≥ 1.30)   → фильтр пройден
```

До фикса здесь было `0.09` и `vol = False`. Сразу после фикса бот начал входить:
`FSM Idle -> QuotingEntryLeg1 | buy Leg1 @ 57.305 (Z=3.20)`.

### 1.3. Побочная находка: `risk.maxPositionLots = 2` урезал персональные лоты

Проверяя фикс на живом портфеле, обнаружил, что **все пары входили двумя лотами**,
хотя в `appsettings.json` стоит `quantityLots` = 55 / 60 / 8 / 2. Причина —
глобальный риск-потолок `risk.maxPositionLots = 2` (значение из ранней версии, когда
позиция всегда была 1 лот). `RiskAndScheduleGuard.clamp_quantity()` молча резал размер,
и весь equal-notional сайзинг из v2.6.2 не работал.

**Что сделано:**

- `risk.maxPositionLots` поднят до `60` — по числу лотов самой крупной пары (MTLR);
- в `fsm._maybe_enter` добавлено предупреждение, если потолок всё же урезал размер
  (раньше это происходило бесшумно);
- тест `test_risk_guard_clamps_preset_lots` фиксирует, что потолок остаётся настоящим
  ограничителем, но при адекватной настройке пары торгуют своим объёмом.

Проверка после правки:

```
AFKS_SBER  2 → 2      IRAO_SBER 8 → 8      MTLR_SBER 60 → 60
SPZ6_SRZ6  1 → 1      VTBR_SBER 55 → 55
```

## 2. Тихий режим вычислений — ПК больше не зависает

Дважды подряд машина уходила в ступор с пропаданием изображения. Причина — мои же гриды:

| Место | `--jobs` было | стало |
|---|---|---|
| `--mode optimize` (`grid_search.py`) | `cpu_count - 1` = **15** | `2` |
| `scripts/pair_grid.py` | 6 | **1** |
| `scripts/portfolio_sim.py` | 6 | **1** |

На i7-10700 (16 логических) 6–15 процессов Python + pandas/numpy с BLAS-потоками по числу
ядер держали 100 % CPU; параллельно работал живой REST-дашборд. На таком профиле отваливался
видеодрайвер (TDR).

**Новый модуль `bot_a/utils/process_guard.py`:**

- `limit_blas_threads()` — `OMP/MKL/OPENBLAS/NUMEXPR/VECLIB/BLIS_NUM_THREADS = 1`
  (вызывается на импорте скрипта, до numpy);
- `lower_priority()` — `BELOW_NORMAL_PRIORITY_CLASS` на Windows, `os.nice(10)` на POSIX;
- `cpu_limit()` = `min(2, cpu//4)`, `hard_limit()` = `min(4, cpu//2)`;
- `resolve_jobs(requested)` — `None` → `cpu_limit()`, явный запрос обрезается до `hard_limit()`;
- `worker_init()` — инициализатор `ProcessPoolExecutor` (приоритет + BLAS в каждом воркере).

Дополнительно в `pair_grid.py` появился `--pause-ms` (по умолчанию 150 мс) — пауза между
прогонами, чтобы не было всплесков; при `--jobs 1` пул не создаётся вообще.

**Замер.** Однопроцессный прогон `VTBR/SBER` 3М: суммарная загрузка CPU **15–26 %**,
CPU-время процесса ~1 ядро. Раньше в пике — 100 % на всех 16 потоках.

**Тесты.** `tests/test_process_guard.py` — 14 проверок: зажим `jobs`, потолок, `cap`,
идемпотентность env-переменных, отсутствие исключений в `lower_priority`,
порядок вызовов в `worker_init`.
