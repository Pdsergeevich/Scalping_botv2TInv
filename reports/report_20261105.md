## 4. Причина: бета `VTBR` не была оценена (и как это сломало всю статистику)

### 4.1. Факт из лога прогрева

```text
Warmup complete: VTBR: tick_count=30108, mu=236.3297, sigma_leg1=0.1808,
                 beta_slow=1.000000, beta_macro=5.259042, beta_drift=н/д
```

`beta_slow = 1.000000` — это **статическая** бета из конфига, оценка не сработала.
Для сравнения, те же строки в тот же день: `MTLR beta_slow=6.557697`, `IRAO beta_slow=1.075207`.

### 4.2. Воспроизведение на кэше ISS (5 дней, без сети)

| пара | свечей | `beta_observations` за 41 940 тиков | итоговая бета |
|---|---|---|---|
| **`VTBR_SBER`** | 3495 / 3494 | **1** | **`1.0000`** (статика) |
| `MTLR_SBER` | 3007 / 3494 | 34 082 | `6.4678` ✓ |
| `IRAO_SBER` | 3432 / 3494 | 35 581 | `1.0821` ✓ |

`beta_observations = 1` — оценщик вызван **один раз за весь прогрев**. Средние ног при этом
посчитаны верно (`mv1 = 57.95`, `mv2 = 298.12` → отношение `5.14`), но до `_set_beta` дело
не дошло, потому что нужно `beta_min_samples = 30`.

### 4.3. Механизм бага (`pair_spread.on_book`)

```python
sampled = gate is None and self._stat_due(book.time_ms)
if self._pending[0] and self._pending[1]:
    self._pending = [False, False]     # ← сброс ВСЕГДА
    if sampled:
        self._update_beta(value1, value2)      # ← вызов ТОЛЬКО тут
```

Флаг `pending` сбрасывается на **любом** событии, где обе ноги в наличии, а `_update_beta`
вызывается только если это же событие оказалось статистическим сэмплом. Если события ног
приходят «парой» на одном таймстемпе (так синтезируются свечи при `phase_lock`), то сэмпл
приходится на событие **одной** ноги (вторая гасит `pending` на следующем событии того же
таймстемпа), и бета не обновляется никогда:

* `MLTR`/`IRAO` — события ног шли с разными таймстемпами, оценка срабатывала на 81 % событий;
* `VTBR` — пара событий на одном таймстемпе, оценка срабатывала на **1 из 41 940**.

В живой сессии тот же дефект дал «ползучую» оценку: `beta_observations` рос примерно
**1 раз в 2 минуты** вместо 1 раза в 5 секунд:

| время MSK | `beta_observations` | бета | `mu` ₽ | `σ` ₽ | `S` ₽ |
|---|---|---|---|---|---|
| `10:03` | 1 | 1.000 | 235.18 | 0.028 | 234.98 |
| `10:30` | 14 | 1.000 | 235.18 | 0.067 | 235.35 |
| `11:00` | 28 | 1.000 | 235.22 | 0.135 | 235.54 |
| **`11:06`** | **34** | **5.252** | 227.54 | **41.76** | **0.85** |
| `11:07` (вход) | 35 | 5.252 | 225.47 | **46.82** | 1.16 |
| `11:30` | 46 | 5.252 | 185.82 | **95.62** | 1.03 |

### 4.4. Цепочка последствий

1. При β = 1.0 спред считался как `S = V2 − V1 ≈ 235 ₽`, хотя при правильной β ≈ 5.25 он
   равен **≈1 ₽**. Значит `mu` стартовал на `234 ₽` выше реальности.
2. В `11:06` бета наконец оценилась → спред мгновенно «прыгнул» с `235` до `0.85 ₽`.
3. `mu` — это EWMA с окном `2400` сэмплов (≈3.3 ч), поэтому она **ползёт** от 235 к 0 часами,
   а `σ` (дисперсия вокруг ползущей средней) раздувается с `0.13` до **95.6 ₽**.
4. Все `Z` после этого — арифметический мусор: `max |Z| = 34.52` (в `10:00:22` было `−43`).
5. Цель тейка считается как `|S − mu| / β × Q × tpDeviationFraction`:
   `|1.05 − 223.31| / 5.252 × 55 × 1.15 = 2676 ₽` → **9733 шага**, цена `6.445` при входе
   `55.110` — то есть цель требовала падения на **88 %**.
6. `v2.9` сняла потолок тейка для пар с β ≥ 0.8 (это было верно для нормальной беты), поэтому
   **ничто не ограничило** безумную цель. В `v2.7/v2.8` тот же расчёт упирался в
   `0.45 %` номинала = `13.6 ₽`, и позиция, скорее всего, закрылась бы тейком.
7. Позиция провисела 16 минут и вышла по «мёртвому спреду» с `−7.15 ₽` gross.

Отдельно: предупреждение `_warn_if_beta_not_estimated` (v2.6.7) **не сработало** — проверка
смотрит на `betaObservations` из `spread_state()`, а там отдаётся счётчик, который к моменту
чтения уже успел подрасти в живой сессии. То есть «страховки» на этот случай фактически нет.

## 7. Дневной предохранитель заблокировал пару на 8 часов

```text
Дневной предохранитель: −8.66731250 RUB <= −5.31808473 RUB (3.5 x комиссия круга)
```

Порог `maxDailyLossFeeMultiple = 3.5` при `fee_rt = 1.52 ₽` даёт лимит **5.32 ₽** — это
*меньше*, чем типичный стоп по σ (`3.5 σ_Leg1` ≈ 10–20 ₽ на 55 лотах). То есть любая
одиночная честная остановка закрывает паре день. После `11:23` `VTBR` не торговал 8 часов,
хотя именно днём спред возвращался.

## 8. Что делать: патч v2.11

### P1 — починить оценку беты (корень сегодняшнего дня)

* В `PairSpreadCalculator.on_book` сбрасывать `pending` **только вместе с потреблением
  сэмпла**; если `sampled`, но одна нога «новая» — обновлять бету по последним известным
  значениям обеих ног (`self._stats`), а не терять наблюдение.
* Регресс-тест: «прогрев `VTBR_SBER` из ISS-кэша даёт `beta_observations ≥ beta_min_samples`
  и `beta > 4`». Сейчас этот тест упал бы.

### P2 — жёсткий гейт: не торговать без оценённой беты

* Пока `beta_observations < beta_min_samples` (или β == статическая), входы запрещены,
  счётчик `betaNotEstimatedSkips`, предупреждение в лог с именем пары.
* Заодно починить `_warn_if_beta_not_estimated` (сейчас не срабатывает) — читать счётчик
  из калькулятора, а не из `spread_state()` после начала сессии.

### P3 — пересевать EWMA при смене беты

* Если β меняется больше чем на `20 %` за один сэмпл (или β отличалась от статической и
  только что оценилась), `mu` := текущий спред, `variance` := минимальная. Иначе `mu`
  ползёт часами, а `σ` раздувается до 95 ₽ — это и есть источник `|Z| = 34`.

### P4 — вернуть абсолютный «предохранитель» тейка

* Потолок `tpMaxNotionalFraction` оставить **всегда** (0.45 % номинала), а `tpCapBetaThreshold`
  использовать только для *дополнительного* ужесточения на парах вида `AFKS` (β < 0.8).
* Плюс санity-проверка «тейк не дальше N шагов / не дальше X % цены» — 9733 шага должны
  отбрасываться как ошибка конфигурации, а не выставляться в стакан.

### P5 — гигиена логов и предохранителей

* Имя пары во всех сообщениях ФСМ (анти-нож, стоп, предохранитель).
* Пересмотреть `maxDailyLossFeeMultiple` для пар с `quantityLots > 10`: привязывать лимит к
  `max(3.5 × fee, 1.5 × σ_Leg1,pos)`.
